01

Verifier-guided search

Best-of-N sampling plus harness-feedback repair, with no extra training. The model sees the exact mismatch (element count, max error, index) or traceback and gets another attempt, which is the multi-turn idea behind Kevin-32B applied at inference time.

02

Data-efficient specialization

Five LLM-serving categories (quantized matmul, prefill attention, KV-cache decode, normalization, RoPE), targeting 60 harness-verified examples each, rather than generic KernelBench breadth. Supervised QLoRA, no RL.

03

Explainability

Every kernel ships with a short rationale: which fusion, tiling, or memory-traffic decision was made and why. Prior systems output code and a benchmark number only.

04

Verified, not claimed

Nothing here is shown as verified unless the harness actually ran on this GPU. When it doesn't run, the UI says why instead of showing a pass or fail.

Honest scope

Limitations

  • Base model today. This demo runs Qwen2.5-Coder-1.5B-Instruct without fine-tuning. The adapter drops into the same pipeline once training finishes, and the badge at the top will change.
  • Small and narrow by design. A 1.5B model and a ~300-example target, positioned against 8B–32B RL-trained systems (KernelLLM, Kevin-32B, AutoTriton), not claiming to beat them on broad benchmarks.
  • Interpreter checks are correctness-only. The Interpreter harness runs kernels through Triton's CPU interpreter on a small shape. It catches indexing, masking, and numerics bugs, but says nothing about speed, and a pass there doesn't count as GPU-verified.
  • No automated explanation metric. Explanations are scored with a manual rubric; there isn't a good automatic one yet.
  • Demo-grade sandbox. Generated code runs in a separate subprocess with a timeout, CPU/file-size limits and a scrubbed environment. That stops hangs, crashes and key leaks, but Python has no airtight sandbox.
