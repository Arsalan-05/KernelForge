Architecture

How it works

KernelForge builds a specialised training set, fine-tunes a small model on it, and verifies every generated kernel with the same automated harness used to build the dataset.

1

Reference templates

15 hand-written Triton kernels across 5 LLM-serving categories — quantized_matmul, attention, kv_cache, norm, and rope — each paired with a PyTorch reference implementation and a correctness test.

2

Verification harness

A subprocess sandbox checks every kernel against its PyTorch reference using seeded inputs, allclose, and median CUDA-event timing. The same harness gates the dataset build, evaluation, and the demo — there is no separate, friendlier check.

3

Dataset

274 of 300 reference kernels verified on a Kaggle T4 (26 rejected for numerical tolerance, timeout, or OOM). Template-level train / val / held-out split (167 / 19 / 88) with no train/test contamination by construction.

4

QLoRA fine-tune

Supervised fine-tuning of Qwen2.5-Coder-1.5B-Instruct on the verified training set using 4-bit NF4 quantization (PEFT / QLoRA). Training is in progress; fine-tuned results are pending.

5

Held-out evaluation

Base model scores 0 / 88 on the held-out set (all generated-code errors, 0 harness errors). Fine-tuned eval: pending.

About the hosted demo: The demo studio generates kernels with a general-purpose hosted model (qwen/qwen3-coder via an API), then verifies them with KernelForge's harness. The fine-tuned adapter is not served yet.

Design decisions

Key properties

01

Verifier-guided search

Best-of-N sampling plus harness-feedback repair, with no extra training. The model sees the exact mismatch (element count, max error, index) or traceback and gets another attempt.

02

Narrow specialization

Five LLM-serving categories (quantized matmul, prefill attention, KV-cache decode, normalization, RoPE), targeting roughly 60 harness-verified examples each, rather than generic KernelBench breadth. Supervised QLoRA, no RL.

03

Explainability

Every kernel ships with a short rationale: which fusion, tiling, or memory-traffic decision was made and why. The model writes the explanation alongside the kernel; it is not a caption added afterwards.

04

Verified, not claimed

Nothing here is shown as verified unless the harness actually ran on that GPU. When it does not run, the UI says why instead of showing a pass or fail.

Honest scope

Limitations

  • Base model in the demo today. The studio generates with qwen/qwen3-coder via API. The fine-tuned adapter is in progress and will drop into this same pipeline once training finishes; the badge at the top will change.
  • Small and narrow by design. A 1.5B model and a ~300-example training set, covering five operator categories — not a broad benchmark.
  • Interpreter checks are correctness-only. The interpreter harness runs kernels through Triton's CPU interpreter on a small shape. It catches indexing, masking, and numerics bugs, but says nothing about speed, and a pass there does not count as GPU-verified.
  • No automated explanation metric. Explanations are scored with a manual rubric; there is not a good automatic one yet.
  • Demo-grade sandbox. Generated code runs in a separate subprocess with a timeout, CPU/file-size limits, and a scrubbed environment. That stops hangs, crashes, and key leaks, but Python has no airtight sandbox.

Data

Dataset

300 candidates from 15 templates × 20 shape configurations. Verified on a Tesla T4; template-level holdout with no train/test contamination.

Project

About KernelForge

KernelForge trains Qwen2.5-Coder-1.5B-Instruct to generate Triton GPU kernels for LLM-serving operators. Each kernel is verified against its PyTorch reference by an automated harness.

Scope

  • Five operator categories: quantized_matmul, attention, kv_cache, norm, rope
  • 15 reference templates, 300 generated candidates, 274 verified on a Kaggle T4
  • Fine-tuned results are pending — training is in progress
  • Research project. Narrow scope by design; not a broad benchmark
